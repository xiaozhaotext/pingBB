# 沙盒消费余额闭环

沙盒复用 `mall.payment.mock.enabled=true`，应用使用 `build:h5:sandbox` 构建。充值能力由 `/member/recharge/payment-options` 返回，沙盒只允许 MOCK，确认到账由服务器写入充值账户及余额流水。正式环境禁止模拟充值确认。

消费余额与收益账户分别记账。分红和奖励沿用现有收益入账流程；沙盒申请提现后，扣减收益、结清冻结金额，按后台配置扣除手续费，将实到金额转入消费余额并完成提现。申请失败时整个事务回滚，相同请求重试不会重复转入。

消费余额可用于自选区余额支付，沿用现有订单结算与库存事务；不足时拒绝购买。个人中心、充值页、收益页均读取服务端余额。

## 应用端与总控后台页面联测

独立 H2/MySQL兼容测试库；登录、商品及订单Mapper使用测试适配器，钱包、收益、库存SQL和订单事务调用实际服务。该验收不等同于远程MySQL环境、真实登录基础设施或真实渠道付款验收。

1. 浏览器登录应用端，实际点击充值100.10元，服务器确认到账，页面余额100.10元。
2. 打开80元自选商品结算页，选择余额支付并提交，订单变为待发货，库存从10减到9，账户余额20.10元。
3. 应用端充值页显示充值 +100.10、订单支付 -80.00、变动后余额20.10。
4. 再次选择80元余额购买，页面显示不可结算并阻止提交；直接请求服务端也拒绝。余额2010分、订单数1、库存9均保持不变。
5. 登录总控后台，进入「财务中心 → 钱包明细管理 → 消费余额与充值」：账户20.10、累计充值100.10、累计余额支付80.00；充值订单已到账，余额流水与应用端一致。

证据：`wallet-browser-evidence.json`、`wallet-recharge-10010.png`、`wallet-after-purchase.png`、`wallet-insufficient.png`、`wallet-admin-ledger.png`。

后台新增接口 `/p0/wallet`，以元的精确字符串返回金额，直接查询应用端的账户、充值订单与余额流水；不复制或重新计算账户余额。会员列表的消费余额也改为同一个账户来源，可提现收益独立显示。订单列表及详情增加余额支付金额，支付类型4显示余额/积分支付。提现统计同时包含已完成状态2和3，按实到金额汇总。

2. 新账号充值100.10元，确认已到账，刷新或重新登录后余额仍为100.10元。
3. 自选区使用余额购买，确认余额按订单实付金额扣减；超出余额购买失败且不产生扣款。
