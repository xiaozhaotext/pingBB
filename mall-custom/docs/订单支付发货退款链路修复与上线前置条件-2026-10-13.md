# 订单支付/发货/退款链路修复与上线前置条件（2026-10-13）

本次目标是让"下单 → 支付 → 发货 → 收货 → 退货退款"这条主链路在代码侧真正闭环，
并把不能靠代码补齐的外部依赖如实列清，避免把"接口存在"当成"可以上线"。

### 1. 订单发货 / 关闭（`OmsOrderServiceImpl`）
- `delivery`：订单必须存在且为"待发货"，强制物流公司与运单号非空，同批去重；
  条件更新行数与订单数不一致即回滚并返回 409；操作历史记录物流公司与运单号。
- `close`：只允许"待付款/待发货"关闭；条件更新校验行数，不符返回 409。

### 2. 退货售后状态机（`OmsOrderReturnApplyServiceImpl`）
- 拆分为"确认退货(0→1) / 完成退货(1→2) / 拒绝退货(0→3)"，全部使用条件 UPDATE。
- 只有"完成退货"那一次状态跃迁才归还库存（按 SKU join 回补 `pms_sku_stock.stock`），
  重复提交不会二次退库；订单内商品全部退完才把订单置为已完成(4)。
- 会员端 `OmsPortalOrderReturnApplyServiceImpl.create` 增加防重复：同订单同商品
  已有"待处理/退货中"申请时拒绝再次提交。

### 3. 真实退款闭环（新增）
- `PaymentRefundService` + `AlipayPaymentRefundServiceImpl`：调用 `alipay.trade.refund`，
  以 `out_request_no = RA{退货单ID}` 保证渠道侧幂等；依次校验
  开关 → 渠道 → 凭证 → 金额，凭证缺失/未启用返回 `SKIPPED`。
- `OrderReturnRefundService`：退货完成时读取 `oms_payment_confirmation`，
  按渠道发起退款，并把结果写入新增表 `oms_refund_record`
  （`SUCCESS` 已退款 / `FAILED` 退款失败待人工 / `SKIPPED` 渠道未启用）。
- `finishReturn` 的操作历史与备注改为**按真实退款结果**书写；
  未配置渠道或无支付记录时如实登记为"待人工退款"，不再写死"已退款"。

### 4. 承运商物流轨迹（新增）
- `LogisticsTrackService` + 快递100实现：按订单真实运单号查询轨迹，
  中文承运商名映射到快递100编码；未启用/未配置凭证/未识别承运商均如实返回原因。
- 后台 `GET /order/logistics` + 订单跟踪对话框展示订单真实节点与承运商轨迹节点。

## 三、真实上线仍缺的东西（外部依赖，非代码问题）

以下能力**代码已就位但需要业务方提供凭证/资质**，在配置前相关接口会按开关如实返回"未接入"：

| 能力 | 现状 | 需要提供 |
|---|---|---|
| 普通订单支付宝支付/退款 | 代码完整（`/alipay/*` + 退款），开关默认 `false` | 支付宝商户 `appId`、应用私钥、支付宝公钥、`sellerId`、备案回调域名 |
| 微信支付（普通订单） | 仅会员购买接入 wechatpay-java，普通订单无微信通道 | 微信商户号、APIv3 密钥、证书；需要新开发普通订单微信通道 |
| 短信验证码 | 无真实短信通道，验证码仅在接口返回（测试用） | 短信服务商账号/签名/模板，未配置前不得视为可用 |
| 承运商物流轨迹 | 快递100适配已接入，开关默认 `false` | 快递100 `customer` + `key` |
| 多商家拆单 | 未实现（商家维度仅到购物车展示） | 业务规则确认后开发 |
| 资金/分销/提现 | 23 条需求保持 **BLOCKED**，不实现 | 合规与业务口径确认前保持关闭 |

> 结论：**代码侧主链路已打通并可测试，但"真实收款/退款/发短信/查物流"必须由业务方提供
> 商户凭证与备案域名后才能上线**。在凭证到位前，请保持相关开关关闭。
